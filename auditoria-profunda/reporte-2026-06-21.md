### Veredicto

EvoFinz es un MVP funcional con un núcleo financiero sólido construido encima de una base técnica frágil. El producto *funciona* para usuarios básicos, pero no sobrevive auditoría técnica: TypeScript sin strict mode, 263K LOC con 9 tests reales, cero CI/CD, un `.env` commiteado en git, y un webhook de pagos que ignora `invoice.payment_failed` — lo que significa que un usuario con tarjeta rechazada sigue con acceso al plan pago durante semanas. Construido rápido con Lovable, lo cual explica tanto sus virtudes (velocidad, completitud funcional) como sus defectos (acoplamiento vertical, god files, migraciones ilegibles, deuda técnica acumulada sin red de seguridad).

### Top 5 Hallazgos Críticos

1. **`stripe-webhook/index.ts:222-227` — `invoice.payment_failed` no hace nada.** El handler solo loguea y rompe el switch. Usuario con tarjeta rechazada conserva acceso al plan pago 2–4 semanas. Pérdida de ingresos directa.

2. **`.env:1-5` commiteado en git (commit `31de8e7`), sin entrada en `.gitignore`.** La anon key y el Project ID de Supabase (`oxrfslyuzcgxacomgzgw`) están en el historial. Cualquier clon expone el endpoint del proyecto.

3. **`tsconfig.app.json`: `strict:false`, `strictNullChecks:false`, `noImplicitAny:false`.** El compilador no detecta null pointer dereferences. Consecuencia directa: 417 anotaciones `:any` explícitas sin advertencia alguna.

4. **Dependencia monolítica en `LOVABLE_API_KEY`** (`supabase/functions/process-receipt/index.ts:121-124`): OCR, chat, contratos, análisis bancario, reconciliación y tax optimizer fallan simultáneamente si la key expira. Sin fallback a ningún otro provider.

5. **`supabase/functions/run-automations/index.ts:312` + `supabase/config.toml:41` — endpoint público sin autenticación.** `verify_jwt=false` y el código no valida ningún Bearer token. Cualquier cliente que conozca la URL puede disparar automations sobre leads arbitrarios.

## 1. ARQUITECTURA

### 1.1 Separación de Responsabilidades

La estructura de carpetas tiene lógica: `components/` por dominio, `hooks/data/` vs `hooks/utils/`, `contexts/`, `pages/`. El problema es que el **acoplamiento vertical rompe esa separación sistemáticamente**.

Componentes de UI acceden directamente a Supabase sin pasar por hooks:

- `src/components/capture/QuickCapture.tsx:802-818` — el componente de cámara llama `supabase.from('documents').delete()` y `supabase.from('expenses').delete()` inline. Lógica de deduplicación mezclada con UI.
- `src/components/chaos/UnifiedChaosInboxPanel.tsx:1035-1066` — mismo patrón: panel visual con lógica de delete de Supabase inline.
- `src/components/chaos/DocumentStatsBar.tsx:28-29` — widget de estadísticas llama `supabase.from('documents').select(...)` y `supabase.from('contracts').select(...)` directamente.
- `src/components/bills/RecurringBillConfirmDialog.tsx:111` — diálogo de UI inserta en `bill_payments` directamente.
- `src/pages/ChaosInbox.tsx:12` — importa `supabase` directamente.

Esto viola el patrón propio de la app y hace que la lógica sea imposible de testear sin montar Supabase real.

## 5. BASE DE DATOS

### 5.1 Esquema General

79+ tablas, bien estructuradas para la complejidad del producto. Migración inicial (`20251120233215`) establece tablas core con FKs hacia `auth.users`, ENUMs y triggers de `updated_at`. Las 126 migraciones muestran evolución orgánica típica de Lovable.

### 5.2 Índices: Ausencias Críticas

**GRAVEDAD: ALTO** — `expenses` e `income` sin índice compuesto en `(user_id, date)`.

Solo existen estos índices para `expenses`:
```
idx_expenses_project_id
idx_expenses_contract_id
idx_expenses_reimbursement_type
idx_expenses_entity_id
idx_expenses_deleted_at  -- partial index para soft delete (buena práctica)
```

Query típico "gastos del usuario X en el mes Y" hace sequential scan completo. Con miles de usuarios, cuello de botella garantizado.

**Índices que faltan:**
```sql
CREATE INDEX CONCURRENTLY idx_expenses_user_date ON public.expenses(user_id, date DESC);
CREATE INDEX CONCURRENTLY idx_income_user_date ON public.income(user_id, date DESC);
CREATE INDEX CONCURRENTLY idx_expenses_user_category ON public.expenses(user_id, category);
CREATE INDEX CONCURRENTLY idx_mileage_user_date ON public.mileage(user_id, date DESC);
```

### 5.3 FKs Faltantes en Tablas Core

Las tablas `income`, `projects` y `savings_goals` (migración `20251204085558`) tienen `user_id UUID NOT NULL` **sin FK declarada**:

```sql
-- income table, líneas 46-62
CREATE TABLE public.income (
  id UUID NOT NULL DEFAULT gen_random_uuid() PRIMARY KEY,
  user_id UUID NOT NULL,  -- Sin REFERENCES auth.users(id) ON DELETE CASCADE
  ...
);
```

Si un usuario de auth es eliminado, los registros de `income` quedan huérfanos.

### 5.4 Calidad de las Migraciones

**124 de 126 migraciones con nombres UUID ilegibles** (ej: `20251120233215_aad9e70d-f8bb-4a51-a6c4-fc0c97841ac5.sql`). Solo 2 tienen nombres descriptivos. Imposible identificar qué hace cada migración sin leerla.

**Dos sistemas de planes paralelos:** ENUM `plan_type` creado como `('free', 'premium', 'pro')`. El código usa también `'bundle'` y `'pro_beta'`. No hay `ALTER TYPE plan_type ADD VALUE 'bundle'` en migraciones. `bundle` se mapea a `"pro"` en el webhook de Stripe; `pro_beta` aparece en `profiles.beta_plan_level` (tipo TEXT). Inconsistencia de esquema latente.

### 5.5 Riesgo de Expiración No Verificada

El frontend lee `is_active` de `user_subscriptions` pero no verifica si `expires_at` ha pasado. Si un webhook de renovación falla, el usuario mantiene acceso al plan pago indefinidamente hasta el siguiente `check-subscription`.

```typescript
  logStep("Payment failed", { invoiceId: invoice.id, customerId });
  break;  // No hace nada con el acceso del usuario
}
```

Con configuración estándar de Stripe (3-4 reintentos en ~2 semanas), el usuario puede tener acceso gratuito semanas después de que su tarjeta fue rechazada.

**GRAVEDAD: MEDIO — Lookup por email, no por `stripe_customer_id`**

```typescript
// stripe-webhook/index.ts:122-132
const { data: profiles } = await supabaseClient
  .from("profiles")
  .select("id")
  .eq("email", email)  // Falla si el usuario cambia su email en Supabase
  .limit(1);
```

**GRAVEDAD: MEDIO — Sin idempotencia en webhook**

No hay tabla de `processed_stripe_events`. Si Stripe reintenta un evento (servidor respondió 5xx), el upsert se ejecuta nuevamente.

**GRAVEDAD: BAJO — Sin manejo de `charge.refunded`**

Reembolsos no manejados. Acceso no se revoca automáticamente.

### 6.4 Puntos Positivos

- `consent_collection: { terms_of_service: 'required' }` (línea 131) — cumplimiento legal.
- `allow_promotion_codes: true` (línea 146) — descuentos habilitados.
- URL de retorno usa `origin` del header, no hardcodeada.
- Sistema de doble verificación (webhook + `check-subscription` en login) es robusto como red de seguridad.

## 7. RENDIMIENTO

### 7.1 Queries y Fetching

El patrón general es bueno: React Query con `queryKey` que incluye userId y filtros, `useDashboardStats` ejecuta 8 queries en paralelo.

**Problema real:** 64 componentes importan `useExpenses` directamente. Cada uno pasa `filters` como objeto nuevo en cada render, generando `queryKey` distintos aunque el rango de fechas sea igual. Sin memoización de los objetos `filters`, esto multiplica requests a Supabase:

```tsx
// FamilyMonthlyAnalysis.tsx:165-168
const { data: expenses } = useExpenses({ dateRange });
const { data: prevExpenses } = useExpenses({ dateRange: prevMonthRange }); // 2do fetch

// MoneyMomentumScore.tsx:41-43
const { data: currentExpenses } = useExpenses({ dateRange: { start: monthStart, end: monthEnd } });
const { data: lastExpenses } = useExpenses({ dateRange: { start: lastMonthStart, end: lastMonthEnd } });
```

**GRAVEDAD: MEDIO — Límite de 500 rows sin paginación**

```ts
// src/hooks/data/useExpenses.ts:13,104
const QUERY_LIMIT = 500;
const { data, error } = await query.order('date', { ascending: false }).limit(QUERY_LIMIT);
```

Usuario con más de 500 gastos nunca ve sus registros históricos. Sin paginación ni infinite scroll.

**`select '*'` en múltiples hooks:** `useAutoReminders.ts:58`, `useBankTransactions.ts:60,85`, y otros trae todas las columnas de tablas anchas.

### 7.2 Re-renders Innecesarios

`useLanguage()` consumido por 924 componentes, función `t` recreada en cada render del provider (ver 2.5). `EntityContext`: 74 componentes re-renderizan en cada update del `selectedEntityId`.

### 7.3 Bundle Size

### 8.3 Bug Crítico de Conversión: iOS Stripe Popup Bloqueado

```typescript
// src/hooks/data/useSubscription.ts:90-106
const { data, error } = await supabase.functions.invoke('create-checkout', {...});
if (data?.url) {
  window.open(data.url, '_blank'); // BLOQUEADO en iOS Safari
}
```

`window.open` después de `await` sale del contexto del evento de usuario. iOS Safari bloquea silenciosamente. El usuario ve el toast "Redirigiendo a Stripe..." pero nada abre. Mismo problema en `openCustomerPortal` (línea 145). **Impide completar pagos en iOS móvil.**

Solución estándar:
```typescript
const win = window.open('about:blank', '_blank'); // ANTES del await
const { data, error } = await supabase.functions.invoke('create-checkout', {...});
if (data?.url && win) { win.location.href = data.url; } else { win?.close(); }
```
